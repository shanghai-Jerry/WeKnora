# Rerank 服务内存优化方案

## 1. 问题分析

### 1.1 当前状况
- 进程 PID 50054，内存占用 19.2GB（峰值 21.9GB）
- 运行 BGE Reranker v2-m3 模型（2.1GB 磁盘大小）
- 使用 PyTorch MPS 后端（Apple Silicon GPU）
- 服务运行时间：1天13小时+

### 1.2 内存占用高的原因
1. **PyTorch MPS 预分配机制**：MPS 后端会预分配大量统一内存（10-20GB），且不完全释放
2. **请求级清理的性能问题**：当前在每个请求结束时调用 `torch.mps.empty_cache()` 和 `gc.collect()`
3. **内存碎片**：19.5GB writable regions 中仅 3.1GB 实际写入

## 2. 并发瓶颈分析

### 2.1 当前方案的问题
```python
finally:
    if scores is not None:
        del scores
    if inputs is not None:
        del inputs
    if device.type == 'mps':
        torch.mps.empty_cache()  # 昂贵操作：同步阻塞，等待MPS设备空闲
    gc.collect()  # 阻塞操作：触发完整GC，受GIL限制
```

### 2.2 高并发场景下的影响
1. **性能下降**：每个请求都执行清理，增加响应时间
2. **资源竞争**：多个线程同时调用 `empty_cache()` 造成竞争
3. **GIL 阻塞**：`gc.collect()` 会暂停当前线程
4. **MPS 效率降低**：频繁调用 `empty_cache()` 反而降低 MPS 内存复用效率

## 3. 优化方案

### 3.1 推荐方案：智能阈值清理 + 定期清理

**核心思路**：
- 移除请求级的 `empty_cache()` 和 `gc.collect()`
- 保留 `del` 语句（轻量级，仅删除引用）
- 使用智能阈值触发清理（基于请求计数或时间间隔）
- 保留后台定期清理任务

**优势**：
- 请求处理路径更轻量，无阻塞操作
- 避免频繁清理造成的性能损耗
- 仍然保证内存不泄漏

### 3.2 实施细节

#### 3.2.1 移除请求级清理
- 删除 `rerank_endpoint` 中的 `torch.mps.empty_cache()` 和 `gc.collect()`
- 保留 `del scores` 和 `del inputs`（这些是轻量级的引用删除）

#### 3.2.2 实现智能阈值清理
使用 FastAPI 中间件或全局计数器：
- 每处理 N 个请求（如 100 个）触发一次清理
- 或每隔 T 秒（如 60 秒）触发一次清理
- 清理操作在后台线程执行，不阻塞请求

#### 3.2.3 优化定期清理任务
- 保持每 5 分钟一次的定期清理
- 添加内存增长检测：如果内存增长超过阈值才清理

### 3.3 备选方案

#### 方案 B：纯定期清理（最简单）
- 完全移除请求级清理
- 仅保留定期清理（每 5 分钟）
- 依赖 Python 自动 GC 和 MPS 内存管理

#### 方案 C：改用 CPU 模式（内存最可控）
- 如果不需要 GPU 加速，改用 CPU
- 内存使用更可预测，但需要评估性能影响

## 6. 预期效果

### 6.1 性能提升
- 请求响应时间降低（移除阻塞清理）
- 高并发时吞吐量提升

### 6.2 内存控制
- 空闲时内存不会无限增长
- 通过定期/阈值清理保证内存回收
- 重启后初始内存应该显著降低（约 2-4GB，取决于模型加载）

## 7. 风险评估

### 7.1 可能的风险
- MPS 内存可能不会立即释放（PyTorch MPS 的限制）
- 如果阈值设置不当，可能导致内存暂时过高

### 7.2 缓解措施
- 设置合理的阈值（建议：100个请求或60秒）
- 保留定期清理作为兜底
- 监控内存增长趋势，必要时调整策略

## 8. 结论

推荐使用 **方案 3.1（智能阈值清理 + 定期清理）**，这是平衡性能和内存控制的最佳方案。如果追求简单，可以使用 **方案 B（纯定期清理）**。
